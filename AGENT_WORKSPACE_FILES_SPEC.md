# Agent Workspace Files Spec

Last updated: June 4, 2026

## Goal

Preserve the fun, user-owned persona files in the UI while moving platform doctrine, capability awareness, and proactive operating behavior into app-managed background files that Canopy can update safely over time.

## Design Principles

- `SOUL.md` remains user-visible and meaningful.
- Stable facts about the human belong in one shared canonical `USER.md`.
- Role-specific learnings belong to the agent that learned them.
- App-managed files are authoritative for safety, permissions, and runtime behavior.
- Repeatable workflows should live in discoverable skills or app-managed playbooks, not be repeatedly stuffed into `SOUL.md`.

## File Ownership

### User-visible and editable

These remain the files shown in the Instructions UI and may be edited by the user. Agents may also update them when appropriate.

- `IDENTITY.md`
- `USER.md`
- `SOUL.md`
- `TOOLS.md`
- `LIBRARY.md`

### Agent-only continuity files

These are not treated as shared persona files.

- `MEMORY.md`
- `HEARTBEAT.md`
- `CAPABILITY_PROPOSALS.md` when introduced
- `.threads/{session_id}/THREAD_STATE.md`
- `.threads/{session_id}/RECENT_HISTORY.md`

### Hidden app-managed files

These are generated by Canopy and are not directly editable through the workspace editor.

- `APP_PROTOCOLS.md`
- `APP_CAPABILITIES.md`
- `APP_OPERATING_MODEL.md`
- `PERMISSIONS.md`
- `DIAGNOSTICS.md`

## Prompt Composition

Effective runtime behavior should come from the combination of:

1. User-visible editable persona files
2. Hidden app-managed files
3. Live capability and diagnostics data
4. Relevant discoverable skills when available

App-managed files are authoritative for:

- security rules
- permission and escalation mechanics
- actual runtime capabilities
- proactive operating guidance

Editable files are authoritative for:

- voice
- taste
- values
- persona expression
- user-authored preferences

Editable files must not be able to weaken app-managed security rules.

## Shared USER.md Model

### Best practice

Use one canonical shared `USER.md` for stable human facts, then mirror it into each agent workspace so the user experience stays playful and local to the agent.

Why:

- every agent should start from the same understanding of the human
- duplication without synchronization creates drift
- role-specific learnings should not pollute the shared human profile

### Canonical storage

Canonical shared path:

- `~/Library/Application Support/Canopy/shared/USER.md`

Mirrored path in each agent workspace:

- `.../workspace/{agent_id}/USER.md`

### Write behavior

- On first-agent onboarding, save the app user profile.
- When the first agent is created, initialize the canonical shared `USER.md` from the saved app user profile and the current template, unless an older agent `USER.md` already exists and should be migrated forward.
- When any visible `USER.md` is saved through the workspace editor, treat that content as the new canonical shared `USER.md` and fan it out to all agents.

### Scope rules

`USER.md` should contain:

- stable identity facts about the human
- preferred names
- timezone
- recurring communication preferences
- durable household or work context

`USER.md` should not contain:

- role-specific observations that only one agent needs
- verbose work logs
- duplicated episodic memories

Those belong in the current agent's `MEMORY.md` or `HEARTBEAT.md`.

## Identity Injection Rules

- The current agent name must always be injected into generated `IDENTITY.md`.
- Renaming an agent must refresh the generated identity scaffold so the file reflects the latest name.
- Personality updates that affect identity-relevant fields should also refresh the generated `IDENTITY.md`.

## Hidden App-Managed Files

### `APP_PROTOCOLS.md`

Contains:

- secure login and credential request rules
- browser intervention flow
- file export rules
- platform-level safety and escalation doctrine

### `APP_CAPABILITIES.md`

Contains:

- current enabled capabilities
- current integrations
- guidance for when to use each capability
- reminders about disabled capability boundaries

### `APP_OPERATING_MODEL.md`

Contains:

- startup checklist
- proactive behavior standard
- first-run "wow moment" expectations
- memory hygiene
- shared-vs-private memory rules
- thread rejoin / continuity rules
- preference for skills over repeated procedural prompt text

## Skills Direction

The preferred long-term pattern is:

- keep `SOUL.md` expressive
- keep hidden app files authoritative
- move repeated workflows into discoverable skills when the runtime supports them cleanly

Good candidates:

- first-run wow playbook
- daily brief
- weekly review
- repo health check
- trip monitor
- budget watch
- memory compaction

## Test Contract

The regression suite should verify:

- `IDENTITY.md` generation injects the latest agent name
- shared `USER.md` is canonical and mirrored to all agents
- saving `USER.md` through the workspace editor updates every agent copy
- app-managed files are generated for each agent workspace
- app-managed files are hidden from artifact drawers and protected from direct editing
- per-thread continuity files are generated for active sessions
